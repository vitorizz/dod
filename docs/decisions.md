# Decisions log

Append new decisions at the bottom. One line of why each.

- **Orchestration layer, not storage layer.** The database never sees the context window; only the harness can capture what was in context at write time.
- **Cross-store from early on.** No single DB vendor can join lineage across Mongo + Postgres + vector DB + framework state. This is the moat.
- **Correctness, not degradation.** Bigger context windows will fix fuzziness; they won't fix false beliefs.
- **Trace + excise, never detection.** Detection is unreliable; tracing from a recorded edge is cheap and reliable.
- **CrewAI first.** Already emits both memory query and memory save events; least glue to a working demo.
- **SQLite append-only store to start.** Simple, local, fast; swap later.
- **Library, not OTel exporter.** OTel loses the retrieval→write binding. Capture ourselves, export as OTel attributes in our own namespace.
- **Open-core.** OSS capture library; paid hosted console. Learned authority layer stays proprietary.
- **Insurance-style pricing.** Small monthly fee by volume/retention, investigations included. Not pay-per-incident.
- **CrewAI: wrap `Memory.recall`/`remember`, not its events.** Save events carry no record ID and handlers run in a thread pool (can reorder); wrapping is synchronous with exact IDs. Scope per agent/task via `contextvars` so concurrent agents never cross-link parents; pin crewai 1.15.22. (2026-09-26, #13)
- **Ask instead of guess: `needs-human` gate before opening a PR.** Agents that guess on unsettled design decisions produce work that has to be redone; a comment + label + stop is cheaper than a wrong PR. The `@claude` reply clears the label and resumes work. (2026-09-27, #17)
- **Content-free ledger.** The ledger stores IDs, content hashes, edges, and metadata only; memory content stays in the customer's stores. This is a requirement on the schema #11 will build, not yet verified against implemented code. (2026-09-27)
- **Instinct as PM layer above the Claude planner.** One owner for roadmap, priorities, and dispatch keeps agents on the highest-value work; the human keeps both gates (`agent-ready`, merge). (2026-10-06, #19)
- **No automated fix-round cap.** The reviewer doesn't emit `@claude` yet, so there's no automated loop to bound; add a cap only if one appears. (2026-10-06, #19)
- **Review after CI, skip docs-only PRs.** Reviewing a PR whose tests fail, or one that only changes Markdown, spends tokens without catching code bugs. (2026-10-06)
- **Self-hosted system, not hosted SaaS.** The paid system runs in the customer's cloud; we never see their data. Supersedes "Open-core... paid hosted console." (2026-09-27, founder decision)
- **Few customers, high ticket.** Annual license sized by deployment, starting with 3–5 design partners. Supersedes "Insurance-style pricing." (2026-09-27, founder decision)
- **Authority layer learns per deployment.** We never see cross-customer data; opt-in anonymized sharing is a later option. The moat shifts to cross-store connectors and reconciliation. (2026-09-27, founder decision)
- **Open-source library builds trust.** Security teams can audit exactly what capture records. (2026-09-27, founder decision)
- **Positioning: lineage for long-lived agent context.** Context managers decide what goes into context; we record what came out because of it, and clean only what's contaminated. Complementary to Mem0, Supermemory, Zep, and markdown-based memory, not competing. Scope covers any agent write (memory, DB, CRM, tickets). (2026-10-07, founder decision)
- **Target: teams building long-lived agents with memory for their users.** Personal agents like Instinct, AI companions, support agents, "agent employees". Instinct-sized startups are design-partner targets; "real forgetting" (deleting a memory plus everything derived from it) is the opening pitch. (2026-10-07, founder decision)
- **Pricing shape: paid pilots, then base fee plus a scaling metric.** Paid pilots first; then an annual license with a base fee plus a metric that scales with the customer (writes tracked or active end users), not seats; a compliance pack (proof of real deletion, audit exports) as an add-on. Refines "Few customers, high ticket." (2026-10-07, founder decision)
- **Edges are tagged `in_prompt` or `retrieved_in_scope`.** Distinguishes items the model actually saw from items retrieved in scope but not necessarily in the prompt. (2026-10-07, founder decision)
- **Over-include rather than miss a parent.** A missed parent breaks trace and excision silently; an extra edge only costs precision, which the tag recovers. (2026-10-07, founder decision)
- **Context scope is the session's context window.** Parents are whatever was in that window at write time, not just the latest retrieval. (2026-10-07, founder decision)
- **Compaction counts as a write.** Compaction rewrites memory; if it isn't captured, lineage breaks at the summary. (2026-10-07, founder decision)
- **Excision offers delete, quarantine (default), and regenerate.** Quarantine is reversible, so it's the safe default when over-inclusion flags clean items. (2026-10-07, founder decision)
- **Duplicate parent with different tags keeps `in_prompt`.** The stronger claim wins; dropping it would understate what the model saw. (2026-10-07, founder decision)
- **Compaction parents are tagged `in_prompt` and include the key's current context.** Compaction reads everything it replaces, and over-inclusion covers whatever else was in the window. (2026-10-07, founder decision)
- **Retrievals default to `retrieved_in_scope`; `in_prompt` only when confirmed.** Claiming an item was in the prompt without evidence would make the tag meaningless for filtering. (2026-10-07, founder decision)
- **Compaction has its own capture call, `on_compaction(key, replaced, ...)`.** A plain write can't carry the set it replaced, and those are its parents. (2026-10-07, founder decision)
- **Ledger checkpoints run off the append path.** SQLite's auto-checkpoint fsyncs inside the commit that crosses the threshold, pushing append p99 to ~4 ms; a background thread on a second connection keeps it ~0.2 ms. (2026-10-07, #11)
- **Writes are ordered by a monotonic `seq`, not `ts`.** Wall-clock time can step backward (NTP, VM migration) and misorder parent/child writes; `seq` (SQLite `AUTOINCREMENT`) never decreases or gets reused, so `ts` is for display only. (2026-10-07, #11)
- **No parent→child index on the append path.** Maintaining `(parent_store, parent_record_id)` inline dirties one B-tree page per distinct parent per commit, which pushed 50-parent append p99 to ~9 ms; blast-radius picks its own indexing strategy when it lands. (2026-10-07, #11)
- **Append-only is enforced by schema triggers, including against `REPLACE`.** `recursive_triggers` is per-connection, so a connection that leaves it off can `INSERT OR REPLACE` past the DELETE triggers; a `BEFORE INSERT` conflict trigger blocks that from any connection. (2026-10-07, #11)
- **CrewAI scopes are entered from `PRE_STEP`/`POST_STEP` interception hooks, not `TaskStartedEvent`.** Event handlers run in a thread pool on a copied context, so a scope set there never reaches the agent; the step hooks run synchronously in the task's own thread or coroutine. (2026-10-07, #13)
- **CrewAI `in_prompt` is decided by the calling crewai function.** The wrapper can't see the prompt, but in 1.15.22 four callers put every recall result into it (`Agent._retrieve_memory_context`, `Agent._prepare_kickoff`, `LiteAgent._inject_memory_context`, `RecallMemoryTool._run`); anything else stays `retrieved_in_scope`. (2026-10-07, #13)
- **CrewAI consolidation is captured by observing storage during `remember`.** crewai 1.15.22 rewrites and deletes similar records on save. Each rewritten or newly saved record becomes a compaction whose parents are every record the consolidation consulted, rewrote or deleted, which over-includes rather than misses a parent. (2026-10-07, #13)
- **CrewAI `remember_many` raises `NotImplementedError` until it is captured.** A loud failure beats a silent lineage gap. It means a crew's automatic post-task save (which crewai logs and swallows) doesn't run while instrumented. (2026-10-07, #13)
- **CrewAI writes record `agent_id` = agent ID and `session_id` = task ID.** The task is the unit of context, and once the write has happened the IDs can't be reconstructed. (2026-10-07, #13)

One scan each of `bindings`, `parents` and `writes` is O(ledger), ~65–100 ms (hardware-dependent) for a root reaching all 10k writes. (2026-10-07, #15)

Each item is recorded as a write at call time, in the caller's scope, and bound when the background save finishes, by matching inserted records' content; items merged into an existing record stay unbound, and the merge is still a compaction. Recording at call time keeps the context edge even if the save runs after the scope ends. (2026-10-08, #13, founder decision)

A missed tombstone is a logged capture gap; a broken `forget` is a user-visible bug. (2026-10-08, #30, founder decision)

- **A scope's context is stored once, as a content-addressed context set.** Copying every context edge onto every write made append cost and ledger size grow with context × writes. `context_sets` (one row per distinct set, keyed by the sha256 of its sorted `(store, record_id, tag)` members) and `context_members` hold it; a write references at most one set (`writes.context_set`) plus its own `direct_parents` (a compaction's replaced items). A grown or re-tagged context is a new set; nothing is updated. Same append-only triggers, no content. The `parents` view joins both into today's one-row-per-edge shape, so `trace`/`blast_radius` are unchanged; where an item is in both, the direct row carries the merged tag (`in_prompt` wins) and hides the context row. - **`append_batch` opens its transaction with `BEGIN IMMEDIATE`.** Its context-set check reads before the first write, so a deferred `BEGIN` would read a snapshot. If another connection or process committed the same new set in between, the upgrade to a write lock failed with `SQLITE_BUSY_SNAPSHOT`, which `busy_timeout` never retries. That dropped the write, a capture gap. Taking the write lock up front waits on `busy_timeout` instead, and the check then sees every committed set. Capture p99 is unchanged, since a single writer gets the lock without contention. (2026-10-08, #37)

- **Blast radius walks a deferred parent→child index, `child_edges`, filled off the append path.** Supersedes "No parent→child index on the append path" and "Blast radius scans the ledger once and walks in memory; no index added." The full scan was O(ledger) per call (~110–190 ms at 10k writes, seconds at 1M). Inline indexes put 50-fresh-parent appends at ~9–20 ms p99, so the append path is unchanged: `child_edges` (`parent_store`, `parent_record_id`, child `seq`, `write_id`, `tag`; primary key on the first three, `WITHOUT ROWID`) is derived from `direct_parents` + `context_members`, append-only, content-free, and filled only by the background checkpoint thread. Batches are sized to hold the write lock ~0.2 ms (≤500 edges/writes), with a pause of ~100× that while writes are arriving, so appends rarely wait and never long. Queries never write: `blast_radius` reads `child_edges` up to the watermark and the rest (the tail) from the source tables in memory, so results are always current. 100k writes: ~1.7 ms for a node with 99 descendants, the root ~1.3–1.5× the old full scan (Edge construction dominates both). Cost: storage grows with edges (a shared context set is expanded per write here), a busy ledger's index lags (idle catch-up ~18 s per 100k writes), and a fill from another process can make an append wait on `busy_timeout`. (2026-10-08, #34, founder decision: option B)

- **A grown context set is stored as a delta over an earlier set (schema version 3).** Since #46 a context that grew by one item stored all its members again, so a long session that retrieves before each write wrote O(context) rows per write. `context_sets` gains `base`, `step` (deltas since the last full set) and `upgrades`; a delta's `context_members` rows are only the members added, or upgraded to `in_prompt`, since its base, and `context_chain` lists the sets whose rows make it up (itself included). The base of step `n` is step `n & (n - 1)` (Fenwick), so a chain has at most log2(N) + 1 parts and step `n` stores the last `n & -n` steps' items (amortized O(log N) per item, and a 128-step delta only once per 128 writes) instead of a linear chain re-stored in full every few levels. N = `_CHAIN_STEPS` = 4096: a full set is re-stored every 4096 steps, so a chain has ≤ 13 parts. The address is still the sha256 of the resolved members, so identical contexts map to one set however they were built. Bases are picked in memory: per `(agent_id, session_id)`, the last set this `Ledger` stored (256 kept, LRU), used when the new context holds all its members with the same or an upgraded tag; otherwise (a shrunk or downgraded context, a new process, another key) the set is stored full, as before. Only sets this `Ledger` committed are bases, so the in-memory chain always matches the file. The ledger also keeps each key's last context read, so a context that extends it reads, validates and sorts only the new items. The `parents` view resolves chains (a `retrieved_in_scope` row is hidden when a later part upgrades it; `upgrades` = 0 skips that check), so `trace`/`blast_radius` are unchanged. - **`blast_radius` walks inside SQLite, on a connection of its own.** Profiling showed whole-ledger walks spent their time building per-level Python state (bindings, children, visited sets) from hundreds of 900-id `IN` queries, not in SQL. A file ledger gets a fresh connection in one read transaction, so the walk sees one snapshot and never holds the ledger lock (a whole-ledger walk would otherwise block appends for its full length); an in-memory ledger has no second connection, so it walks on the ledger connection under the lock and drops the temp tables after. - **We don't store agent memory; we record its lineage. The ledger is that lineage graph, stored in SQLite.** Memory lives in the customer's stores (CrewAI, LangGraph, Anthropic's file-based memory tool, graph memories like Zep), which we instrument; how they store memory is their choice, and we stay complementary to all of them. - **The lineage index is integers in the ledger's own shape, in a companion file `<ledger>-lineage`.** Supersedes "Blast radius walks a deferred parent→child index, `child_edges`, filled off the append path." `child_edges` had one row per (write, context item), so a shared context set was re-expanded for every write that used it, and walks moved 32-character strings through temp tables. The index now interns each `(store, record_id)` as an integer (`items`) and follows what the ledger stores: `direct_children`, `part_items` (context-set parts holding an item), `set_parts` (sets whose chain includes a part), `set_writes`, `write_items` (bindings). Its size follows the ledger, and a walk expands each item, part and set once. It lives in its own SQLite file, attached as `lineage`, because it is derived: filling it then takes only that file's write lock, never the ledger's, so appends never wait for a fill. Being derived, it is rebuilt rather than migrated: a missing file, one at another `INDEX_VERSION`, an unreadable one, or one whose watermark keys (the write ID, set hash and binding at each watermark) don't match the ledger (a restored backup, a copied file) is deleted and refilled. The fill is pure SQL (`INSERT … SELECT` from the ledger), and it takes the lineage file's write lock before reading the watermarks, so concurrent fills never duplicate rows. A walk reads the watermarks first, so the ledger snapshot it then reads holds everything the index came from. Measured on a dev machine: 10k-write root ~50–85 ms (was ~125–185 ms), 100k root ~0.65–0.9 s (was ~1.35–1.5 s), a 99-descendant result ~0.65 ms (was ~2–3 ms). The bars are now the targets, 100 ms and 1 s, timed once the background fill has caught up. A separate 250 ms bar covers a fully unindexed 10k walk (~150 ms, all from the source tables), which is what a walk pays for writes the fill hasn't reached. (2026-10-08, #66)
- **Schema version 4 drops `child_edges` and `child_edges_filled`; version-3 files migrate in place.** Nothing else in the ledger changed, and both tables are derived, so dropping them loses nothing: opening a version-3 file drops them and sets version 4 in the open transaction. - **While writes are arriving, the background fill runs at most ~2% of the time; when they stop, it catches up at full speed.** Even without the write lock, an in-process fill slowed appends (50-fresh-parent p99 ~0.6 → ~1.2–1.6 ms). The cause is SQLite's process-wide memory-statistics mutex (on by default in the system and python.org builds), which every allocation on every thread takes. The same fill in another process, or with that statistic turned off, left p99 at baseline. A library can't safely change SQLite's global configuration and shouldn't spawn processes, so the fill stays out of the way instead. While busy it takes ≤200 writes per transaction and rests 49× its own run time, checking every 100 ms whether writes have stopped so it starts catching up right away (a 10k-write burst is indexed ~0.7 s after the last append); idle, it takes 1,000 per transaction back to back, polling every 20 ms. Writes count as arriving until none has for 100 ms. This keeps up with sustained writes at realistic rates (100/s with a 20-item context: lag ≤ 4 writes; 1,000/s with 2 parents: lag ≤ ~60). Under heavier sustained load the index lags, queries read the rest from the source tables (still exact, slower), and it catches up during the pauses agents spend waiting on model calls. Append p99 has priority over index freshness. (2026-10-08, #66)

- **Capture completeness is checked by `reconcile`, which compares each store with the ledger, read-only.** Capture can't see writes that bypass the instrumented calls (direct inserts, uninstrumented clients, TTL sweeps, hand-edited memory files), so CLAUDE.md's biggest risk is checked after the fact instead. Reconcile reports four kinds of item:
  - `unrecorded`: in the store, never bound.
  - `resurrected`: in the store, but last event is a tombstone.
  - `missing`: live in the ledger, gone from the store.
  - `modified`: content hash differs from the last bound write's.
  An item is live when its last binding (by append order) is newer than its last tombstone (by `ts`). Unrecorded and resurrected items list the recorded writes that took them as parents (`read_into`), because those are where trace breaks.

  It reads each store first and the ledger after, because a bind lands just after the store call. Every first-pass finding is then re-checked item by item after `grace` (default 1 s), so in-flight writes and deletes aren't reported. It is read-only, for two reasons. Recording reconcile runs, or adopting unrecorded items as writes, needs schema and semantics decisions (an unrecorded item's true parents are unknowable). And an audit tool should not change what it audits. Adapters read around capture so reconciling records no retrievals. A store that can't be read raises; it is never reported as empty. Stores the ledger has bindings for but that weren't passed in are listed in `unchecked`, so a blind spot is visible. Cost is one pass per store plus one over the ledger's source tables, with each source table scanned once against small temp tables: 100k items ~1 s; 100k context-heavy writes with 2,000 findings read into ~600k writes ~3.7 s. - **Postgres is supported through LangGraph's `PostgresStore`, not a SQL-level integration.** `PostgresStore` keeps `BaseStore`'s routing (it implements only `batch`/`abatch`), so the existing LangGraph integration captures it with no new code, including pgvector `search` results as parents, quarantine filtering, delete adapters and reconcile (which also finds rows inserted with raw SQL). Capturing arbitrary SQL would need a record-ID scheme for rows and a way to see which rows reach the context; deferred until a design partner needs it. `[postgres]` pins langgraph-checkpoint-postgres 3.1.2, the last release compatible with our langgraph-checkpoint 4.2.0 pin. (2026-11-04)
- **The demo console draws the ledger by turn and version, not by item.** v1 drew one box per item: a conversation thread was one box holding every message and reply, every box had edges from everything in its turn's context, and writes in the same turn linked to each other, so tracing a reply and tracing its conversation looked the same. v2 makes each turn a row, a box one version of an item written in that turn, and draws only reads: a turn's parents resolved to the version that existed when the turn began. Trace walks these reads turn by turn, with customer messages as origins; blast radius and excise still use dod's item-level `blast_radius`/`excise`, so what's shown is what's quarantined. (2026-11-04)
- **The ledger is tamper-evident through an opt-in hash chain (`audit=True`) written in the same transaction as the rows, not by a background sealer.** A background sealer would also seal rows inserted outside the library (or would have to write the ledger file from the background, which only the write connection does); sealing in the transaction costs ~0.04 ms per append, enough to push CI's tightest default benchmarks over their bars, so it's off by default and benchmarked separately. Truncating the newest entries can't be detected from the file, so `head()` is meant to be anchored outside it. (2026-11-05)
- **Context members are covered by their set's content address, not hashed into the chain.** The set hash is already sha256 of the merged members, so `verify` recomputes it; hashing the members too cost ~0.1 ms per write with 50 fresh context items, enough to threaten the p99 bar. (2026-11-05)
- **The first audited open seals the rows already in the file in one entry** (a migrated version-5 file, or one used without `audit`). Earlier edits can't be detected, but every row is then covered and any later edit is; leaving old rows unchained would make "unchained" ambiguous between legacy and forged. Rows appended later without `audit` are reported as unchained. (2026-11-05)

- **`in_prompt` is confirmed from the prompt actually sent, by text.** Integrations can't see the prompt, so retrievals stay `retrieved_in_scope` (decision above); the model call can. Integrations pass each retrieved item's content to `on_retrieve(texts=...)`; `Capture` keeps, per key and in memory only, one probe per string (its first 64 whitespace-normalized characters, at least 12, up to 8 per item), and `confirm(prompt)` upgrades every item with a probe in the prompt. The start of a text survives a prompt that truncates it; a paraphrase or summary doesn't match and stays `retrieved_in_scope`, which over-includes rather than misses. Confirmation only upgrades: it never drops a parent, and writes before it keep their tags (append-only). Probes are cleared with the key's context, so the ledger stays content-free. (2026-11-05)
- **Prompt confirmation hooks the model client, not a framework.** `instrument_anthropic` / `instrument_openai` wrap the instance's request methods and pass every string in the request (system, messages, tool results, tool inputs) to `dod.prompt.confirm` before the call; nothing in the request changes. Any other client calls `dod.prompt.confirm(text)` itself. It runs on the scope's key across every registered `Capture`, so one confirmation covers every store. (2026-11-05)
- **`blast_radius` and `excise` take `in_prompt_only`.** The walk follows a direct parent or a context-set part only where its own row is `in_prompt`; an upgrade is stored as an `in_prompt` row in a later part, so sets whose chain includes it are reached and earlier sets aren't, with no schema change. The default stays the over-including walk; `in_prompt_only` is the precise view once prompts are confirmed. (2026-11-05)
- **The PyPI distribution is `dod-lineage`; the import name stays `dod`.** `dod` is taken on PyPI by an unrelated project. Renaming the import would break every user's code for a packaging detail. (2026-11-05)
- **The CLI only quarantines.** Deleting goes through each store's delete adapter, which needs a live, instrumented store object the CLI can't construct; quarantine is reversible and needs only the ledger, so it's the safe action for an operator at a terminal. (2026-11-05)

- **`trace` resolves a parent item only to versions written before the child (by `seq`).** It used to resolve an item to every write bound to it, so tracing an early write listed later versions of its parents (a thread's later turns, a file rewritten afterwards) as ancestors. A version written after the child can't have been in its context; every earlier version still is, so this removes impossible ancestors without dropping a possible one. A parent with no earlier version is reported in `unrecorded`. It also makes cycles impossible to follow (every edge goes back in `seq`). `blast_radius` keeps the item-level walk (it may over-include a child that read the item before the reached version was written), since a per-version forward walk needs seq bookkeeping per expanded item; tracked as a follow-up. (2026-11-05)
- **Mem0's internal retrieval inside `add` is recorded as the added memories' `in_prompt` parents.** Mem0 searches existing memories and feeds the matches to its extraction LLM, so they are exactly what was in context at the write; without it, memory-to-memory lineage inside Mem0 would be invisible unless the agent also searched. It is collected by wrapping the instance's `vector_store.search` only while an `add` runs. (2026-11-05)

- **TypeScript capture is native and writes the Python ledger format (option A of `docs/typescript.md`).** No daemon to run, the same guarantees, and one ledger for mixed deployments. The schema is generated from Python, and a compatibility test checks hashes and content addresses byte for byte, so the two can't drift silently. (2026-11-06)
- **The TS package uses Node's built-in `node:sqlite` (Node >= 22.13), with no runtime dependencies.** A capture library that installs no native module is easier to adopt and audit than one built on `better-sqlite3`. Node 22 is the active LTS. (2026-11-06)
- **TS stores context sets as full sets, not Python's Fenwick delta chains.** The Python readers treat a full set as a one-part chain. Porting the delta logic would double the code that must stay byte-compatible, to save storage on long scopes. Revisit if TS ledgers grow large. (2026-11-06)
- **TS refuses to write audited ledgers.** Writes from TS would be unchained, so `verify` would report them as tampering. Porting the chain is possible later. (2026-11-06)
- **TS checkpoints the WAL from a worker thread with autocheckpoint off,** as Python does from its checkpoint thread. With SQLite's default autocheckpoint, one commit in ~1000 ran the checkpoint and capture p99 was ~0.6–0.8 ms; with the worker it is ~0.2–0.4 ms. (2026-11-06)
- **Per-version precision going forward is an opt-in post-filter (`blast_radius(precise=True)`), not a change to the SQL walk.** The walk stays item-level and tuned. The filter visits the reached writes once in `seq` order, keeping a write only if one of its edges comes from a kept version written before it (parents' versions always precede their children in `seq`). This resolves the follow-up noted in the `trace` versions entry above. Default stays over-inclusive, the safe side. (2026-11-06)
- **The library is licensed Apache-2.0.** It is permissive, so teams can embed capture in commercial agents. Its explicit patent grant is what security and legal reviews of an open-source dependency look for. It doesn't restrict the separate self-hosted system. (2026-11-06)
- **Cross-host lineage ships local ledgers to Postgres (option A of `docs/postgres-ledger.md`), rather than appending to Postgres.** Capture stays local and sub-millisecond, and a Postgres outage never blocks an agent; cross-node lineage lags by one shipping interval. Rows are copied by per-table watermark with `ON CONFLICT DO NOTHING`, so a crash re-ships at most a batch. Context sets are content-addressed, so nodes share them. (2026-11-06)
- **The shipper runs as its own process (`dod ship`).** As a thread in the agent's process it held the GIL while building batches, and capture p99 jumped to 1.0–1.3 ms while shipping every 100 ms; from a separate process, capture p99 stays around 0.1 ms. (2026-11-06)
- **Quarantine fans out by pulling: each node appends other nodes' quarantine rows to its own ledger with actor `dod-ship:<node>`, and never ships those back.** Every node's instrumented stores then filter the item with the existing quarantine cache, with no new code on the capture path. Actions are applied in pull order (by time); there is no global order across nodes. (2026-11-06)
- **`PgLineage.trace` resolves a parent to versions written at or before the child by timestamp.** Nodes share no sequence; within one node this matches the local `seq` rule (checked on a random graph). (2026-11-06)
- **Cross-node excision writes quarantine rows into Postgres under a reserved node, `dod-console`, and lets the existing pull fan them out.** No new channel to the nodes, and every node applies it the same way as a quarantine from a peer. The node name is reserved, so a shipper can't take it. The node's `seq` is kept dense under an advisory lock. (2026-11-06)
- **The writer restarts the WAL (`wal_checkpoint(TRUNCATE)`, no busy wait) after a commit once the file passes 64 MiB.** With autocheckpoint off, SQLite only restarts the WAL when a writer begins at a moment the log is fully copied and unread. Under continuous writes, with the index fill reading, that never happened: in the 1,000-record reset benchmark the WAL reached 2.4 GB, and commits slowed with it (CI p99 150–330 ms). Now it stays bounded. The restart costs the commit that triggers it (a checkpoint of the remaining frames and a disk sync, ~100 ms locally and several hundred on CI disks), once per 64 MiB of writes. That is far below 1% of writes in normal capture, so it doesn't reach p99. The 5 MB-per-call reset benchmark guards its median instead of p99. RESTART without truncating was cheaper per reset, but the file then never shrinks, so its size can't signal the next one, and Python's sqlite3 exposes no WAL hook. Checkpointing early in the background as the WAL filled was also tried: it ran a disk sync on every pass and raised capture p99 on CI. (2026-11-06)

# Decisions log

Append new decisions at the bottom. One line of why each.

- **Orchestration layer, not storage layer.** The database never sees the context window; only the harness can capture what was in context at write time.
- **Cross-store from early on.** No single DB vendor can join lineage across Mongo + Postgres + vector DB + framework state. This is the moat.
- **Correctness, not degradation.** Bigger context windows will fix fuzziness; they won't fix false beliefs.
- **Trace + excise, never detection.** Detection is unreliable; tracing from a recorded edge is cheap and reliable.
- **CrewAI first.** Already emits both memory query and memory save events; least glue to a working demo.
- **SQLite append-only store to start.** Simple, local, fast; swap later.
- **Library, not OTel exporter.** OTel loses the retrieval→write binding. Capture ourselves, export as OTel attributes in our own namespace.
- **Open-core.** OSS capture library; paid hosted console. Learned authority layer stays proprietary.
- **Insurance-style pricing.** Small monthly fee by volume/retention, investigations included. Not pay-per-incident.
- **CrewAI: wrap `Memory.recall`/`remember`, not its events.** Save events carry no record ID and handlers run in a thread pool (can reorder); wrapping is synchronous with exact IDs. Scope per agent/task via `contextvars` so concurrent agents never cross-link parents; pin crewai 1.15.22. (2026-09-26, #13)
- **Ask instead of guess: `needs-human` gate before opening a PR.** Agents that guess on unsettled design decisions produce work that has to be redone; a comment + label + stop is cheaper than a wrong PR. The `@claude` reply clears the label and resumes work. (2026-09-27, #17)
- **Content-free ledger.** The ledger stores IDs, content hashes, edges, and metadata only; memory content stays in the customer's stores. This is a requirement on the schema #11 will build, not yet verified against implemented code. (2026-09-27)
- **Instinct as PM layer above the Claude planner.** One owner for roadmap, priorities, and dispatch keeps agents on the highest-value work; the human keeps both gates (`agent-ready`, merge). (2026-10-06, #19)
- **No automated fix-round cap.** The reviewer doesn't emit `@claude` yet, so there's no automated loop to bound; add a cap only if one appears. (2026-10-06, #19)
- **Review after CI, skip docs-only PRs.** Reviewing a PR whose tests fail, or one that only changes Markdown, spends tokens without catching code bugs. (2026-10-06)
- **Self-hosted system, not hosted SaaS.** The paid system runs in the customer's cloud; we never see their data. Supersedes "Open-core... paid hosted console." (2026-09-27, founder decision)
- **Few customers, high ticket.** Annual license sized by deployment, starting with 3–5 design partners. Supersedes "Insurance-style pricing." (2026-09-27, founder decision)
- **Authority layer learns per deployment.** We never see cross-customer data; opt-in anonymized sharing is a later option. The moat shifts to cross-store connectors and reconciliation. (2026-09-27, founder decision)
- **Open-source library builds trust.** Security teams can audit exactly what capture records. (2026-09-27, founder decision)
- **Positioning: lineage for long-lived agent context.** Context managers decide what goes into context; we record what came out because of it, and clean only what's contaminated. Complementary to Mem0, Supermemory, Zep, and markdown-based memory, not competing. Scope covers any agent write (memory, DB, CRM, tickets). (2026-10-07, founder decision)
- **Target: teams building long-lived agents with memory for their users.** Personal agents like Instinct, AI companions, support agents, "agent employees". Instinct-sized startups are design-partner targets; "real forgetting" (deleting a memory plus everything derived from it) is the opening pitch. (2026-10-07, founder decision)
- **Pricing shape: paid pilots, then base fee plus a scaling metric.** Paid pilots first; then an annual license with a base fee plus a metric that scales with the customer (writes tracked or active end users), not seats; a compliance pack (proof of real deletion, audit exports) as an add-on. Refines "Few customers, high ticket." (2026-10-07, founder decision)
- **Edges are tagged `in_prompt` or `retrieved_in_scope`.** Distinguishes items the model actually saw from items retrieved in scope but not necessarily in the prompt. (2026-10-07, founder decision)
- **Over-include rather than miss a parent.** A missed parent breaks trace and excision silently; an extra edge only costs precision, which the tag recovers. (2026-10-07, founder decision)
- **Context scope is the session's context window.** Parents are whatever was in that window at write time, not just the latest retrieval. (2026-10-07, founder decision)
- **Compaction counts as a write.** Compaction rewrites memory; if it isn't captured, lineage breaks at the summary. (2026-10-07, founder decision)
- **Excision offers delete, quarantine (default), and regenerate.** Quarantine is reversible, so it's the safe default when over-inclusion flags clean items. (2026-10-07, founder decision)
- **Duplicate parent with different tags keeps `in_prompt`.** The stronger claim wins; dropping it would understate what the model saw. (2026-10-07, founder decision)
- **Compaction parents are tagged `in_prompt` and include the key's current context.** Compaction reads everything it replaces, and over-inclusion covers whatever else was in the window. (2026-10-07, founder decision)
- **Retrievals default to `retrieved_in_scope`; `in_prompt` only when confirmed.** Claiming an item was in the prompt without evidence would make the tag meaningless for filtering. (2026-10-07, founder decision)
- **Compaction has its own capture call, `on_compaction(key, replaced, ...)`.** A plain write can't carry the set it replaced, and those are its parents. (2026-10-07, founder decision)
- **Ledger checkpoints run off the append path.** SQLite's auto-checkpoint fsyncs inside the commit that crosses the threshold, pushing append p99 to ~4 ms; a background thread on a second connection keeps it ~0.2 ms. (2026-10-07, #11)
- **Writes are ordered by a monotonic `seq`, not `ts`.** Wall-clock time can step backward (NTP, VM migration) and misorder parent/child writes; `seq` (SQLite `AUTOINCREMENT`) never decreases or gets reused, so `ts` is for display only. (2026-10-07, #11)
- **No parent→child index on the append path.** Maintaining `(parent_store, parent_record_id)` inline dirties one B-tree page per distinct parent per commit, which pushed 50-parent append p99 to ~9 ms; blast-radius picks its own indexing strategy when it lands. (2026-10-07, #11)
- **Append-only is enforced by schema triggers, including against `REPLACE`.** `recursive_triggers` is per-connection, so a connection that leaves it off can `INSERT OR REPLACE` past the DELETE triggers; a `BEFORE INSERT` conflict trigger blocks that from any connection. (2026-10-07, #11)
- **CrewAI scopes are entered from `PRE_STEP`/`POST_STEP` interception hooks, not `TaskStartedEvent`.** Event handlers run in a thread pool on a copied context, so a scope set there never reaches the agent; the step hooks run synchronously in the task's own thread or coroutine. (2026-10-07, #13)
- **CrewAI `in_prompt` is decided by the calling crewai function.** The wrapper can't see the prompt, but in 1.15.22 four callers put every recall result into it (`Agent._retrieve_memory_context`, `Agent._prepare_kickoff`, `LiteAgent._inject_memory_context`, `RecallMemoryTool._run`); anything else stays `retrieved_in_scope`. (2026-10-07, #13)
- **CrewAI consolidation is captured by observing storage during `remember`.** crewai 1.15.22 rewrites and deletes similar records on save. Each rewritten or newly saved record becomes a compaction whose parents are every record the consolidation consulted, rewrote or deleted, which over-includes rather than misses a parent. (2026-10-07, #13)
- **CrewAI `remember_many` raises `NotImplementedError` until it is captured.** A loud failure beats a silent lineage gap. It means a crew's automatic post-task save (which crewai logs and swallows) doesn't run while instrumented. (2026-10-07, #13)
- **CrewAI writes record `agent_id` = agent ID and `session_id` = task ID.** The task is the unit of context, and once the write has happened the IDs can't be reconstructed. (2026-10-07, #13)
- **Blast radius scans the ledger once and walks in memory; no index added.** Without a parent→child index, a per-level query or recursive CTE rescans `parents` at every level, and a CTE without a visited set enumerates paths, which explodes on diamonds. One scan each of `bindings`, `parents` and `writes` is O(ledger), ~65–100 ms (hardware-dependent) for a root reaching all 10k writes. (2026-10-07, #15)
- **CrewAI scopes clear their context on exit, not just on entry.** Task IDs are fresh UUIDs, so a key is never re-entered and an entry-only reset would hold every finished task's context for the life of the process. (2026-10-08, #13)
- **A save's compactions and binds go to the ledger in one transaction (`Ledger.append_batch`, `Capture.on_batch`).** One commit per compaction and bind put a consolidating CrewAI `remember()` at 8 commits and p99 ~11 ms; batched, it is 2 commits and p99 ~0.4 ms. (2026-10-08, #13, founder decision)
- **A delete-only CrewAI consolidation is a compaction bound to the record `remember()` returned, with the deleted records as parents.** Otherwise the deletion leaves no trace in the ledger; a deletion row in the schema is left for its own issue. (2026-10-08, #13, founder decision)
- **CrewAI `remember_many` is captured, not rejected.** Supersedes "`remember_many` raises `NotImplementedError`". Each item is recorded as a write at call time, in the caller's scope, and bound when the background save finishes, by matching inserted records' content; items merged into an existing record stay unbound, and the merge is still a compaction. Recording at call time keeps the context edge even if the save runs after the scope ends. (2026-10-08, #13, founder decision)
- **The `remember_many` benchmark pauses 2 ms between calls.** Each call writes ~80 KB of WAL, so a tight loop runs at ~200 MB/s and measures the kernel's writeback throttling (~3% of calls at ~10 ms) rather than capture; a real batch spends much longer embedding and in the LLM. (2026-10-08, #13)
- **On-disk benchmarks report the median p99 of three rounds; the bar stays 1 ms.** A shared CI runner's disk can stall one round to ~11 ms while the others sit at ~0.4 ms; the median keeps the 1 ms bar meaningful without loosening it. (2026-10-08, #13)
- **CrewAI `update()` and `forget(record_ids=...)` are captured as compactions; filter deletes warn.** A direct edit or deletion is a write, so `update` is a compaction of its record (bound to it) and `forget` an unbound compaction of the given IDs, both `agent_inference` since neither takes a source. `forget` without IDs, `reset` and `reset_all` can't name what they delete, so they pass through with a warning on every call. (2026-10-08, #13)
- **write_id is time-ordered (UUIDv7 layout) so index inserts append at the right edge; random IDs dirtied one B-tree page per write per index.** IDs strictly increase within a process (previous + 1 within a millisecond or if the clock steps back), so successive writes' IDs sort by creation. (2026-10-08, #13, founder decision)
- **The `remember_many` benchmark times its call-time commit and its background bind commit separately, each p99 < 1 ms.** The caller waits only for the call-time commit; the bind runs later on crewai's save pool. Storing a batch's shared context once is #37. (2026-10-08, #13, founder decision)
- **Batch capture calls are held to p99 < 1 ms per write, with a 2 ms ceiling per call, until #37.** `remember_many` records one write per item, each carrying the scope's full context, so its call-time commit sits near 1 ms for 5 items. The bar in CLAUDE.md is per write; the ceiling guards regressions, and #37 (shared context stored once) restores a 1 ms per-call bar. Refines the entry above. (2026-10-07, #13)
- **Quarantine is an append-only log of `quarantine`/`release` actions per `(store, record_id)`; the latest by `seq` wins.** Nothing is deleted or updated, so quarantine stays reversible and auditable, and the ledger stays content-free (`reason`/`actor` are caller-supplied text). (2026-10-08, #32)
- **CrewAI `recall` drops quarantined results before they reach the caller or the context.** A quarantined item must stop spreading, so it can't become a parent of new writes. Dropped results are counted per item in memory (`blocked_retrievals()`). (2026-10-08, #32)
- **The recall filter caches the quarantined set and applies only actions past the last `seq` it saw (`Ledger.quarantine_log`).** Re-reading the whole set on every change cost ~3.7 ms per recall with 1,000 items; the incremental catch-up is one index seek per recall (~0.03 ms p99) and ~0.09 ms right after a change. It reads on its own connection so it never waits behind an append's commit, and sees changes from any process. (2026-10-08, #32)
- **Blocking reviews trigger an automated fix, capped at 3 rounds.** The review ends with `BLOCKING: <count>`; above 0 it posts `@claude fix the blocking items in the latest review` (PAT_TOKEN, so `claude.yml` fires). After 3 such comments on a PR it adds `needs-human` instead, so a fix that can't converge stops spending tokens. Supersedes "No automated fix-round cap." (2026-10-07)
- **Open PRs are auto-updated after every push to main.** Merging main into behind PRs (PAT_TOKEN, so CI and review rerun) keeps green checks meaning "green on current code"; a merge conflict gets a comment listing the files plus `needs-human`, since resolving it is a judgment call. PRs already labeled `needs-human` are skipped to avoid re-commenting on every push. If the latest `needs-human` came from this workflow's conflict comment (hidden marker, label added right after it) and the PR now merges cleanly, the label is removed automatically; labels from other causes are left alone because only conflicts can be checked mechanically. (2026-10-07)
- **Blocking findings only in `.github/workflows/` go straight to `needs-human`.** The GitHub App can't push workflow changes, so a fix round there can't succeed; the review lists one `BLOCKING_FILE:` line per finding so the script can tell. (2026-10-07)
- **Workflow shell logic lives in `scripts/*.sh`; the review job runs the base branch's copy.** Scripts are testable with a fake `gh`, but unlike workflows an agent run can edit them, and that step holds `PAT_TOKEN`. (2026-10-07)
- **Deletions are append-only tombstone rows: `(store, record_id)`, `reason` (`consolidation`, `excision`, `forget`, `other`), an optional causing `write_id`, and `agent_id`/`session_id`.** Without them a deletion leaves no trace and a "forget" can't be audited. Tombstones have their own `seq`, the same append-only triggers, no content, and never hide an item's writes or edges: trace and blast-radius still walk through a deleted item and report its tombstones in `deleted`. Indexed by `(store, record_id)` on the append path, since deletions are rare. (2026-10-08, #30)
- **CrewAI consolidation deletes are tombstones, naming the `remember` write that caused them.** Supersedes "A delete-only CrewAI consolidation is a compaction bound to the record `remember()` returned". A delete-only consolidation now records no compaction; rewrites and inserts are still compactions with the deleted records as parents. In a `remember_many` of several items, which item's save deleted a record is unknown, so the tombstone's `write_id` is empty. (2026-10-08, #30)
- **CrewAI `forget`, `reset` and `reset_all` record a tombstone (reason `forget`) per deleted record, found by listing storage before and after the delete.** Supersedes the `forget` and filter-delete half of "CrewAI `update()` and `forget(record_ids=...)` are captured as compactions; filter deletes warn" (`update` is unchanged). The storage API returns only a count and backends apply filters differently, so a before/after diff is exact where re-implementing the filter isn't. It runs inside crewai's call, after `reset` drains pending saves. `forget(record_ids=...)` with no other filter checks only those IDs. The actor is the current scope's agent and task; `forget` no longer records the scope's context as parents, since a deletion has no derived content. (2026-10-08, #30)
- **Tombstones replace the interim deletion captures from #13 (founder decision, delegated; #30).** Supersedes "A delete-only CrewAI consolidation is a compaction bound to the record `remember()` returned, with the deleted records as parents" and the `forget`/filter-delete half of "CrewAI `update()` and `forget(record_ids=...)` are captured as compactions; filter deletes warn". Those were stand-ins until the schema had a deletion row. `forget(record_ids=...)` now records a tombstone per deleted record instead of an unbound compaction with the scope's context as parents; a deletion derives no content, so it has no parents. Filter deletes are now recorded instead of warning. (2026-10-08, #30, founder decision)
- **Deletes by filter (`forget()` without IDs, `reset()`, `reset_all()`) are held to a per-call ceiling of 100 ms for 1,000 records, not the 1 ms bar.** They are off the hot path (an explicit wipe, not part of an agent step) and list the store before and after, so their cost scales with store size. Measured ~54 ms on a dev machine; 100 ms guards regressions without flaking. `forget(record_ids=[x])` is the common case and keeps the 1 ms bar. (2026-10-08, #30, founder decision)
- **Duplicate tombstones for one `(store, record_id)` are all kept.** The ledger is append-only, and each tombstone records a distinct event (e.g. a consolidation, then a `forget` racing it). Readers treat an item as deleted if any tombstone exists. (2026-10-08, #30, founder decision)
- **Delete capture never changes the host's delete.** If listing records fails (backend lacks `get_record`/`count`/`list_records`, or raises), a warning is logged, nothing is recorded, and the delete runs as uninstrumented. A failing post-delete listing or tombstone commit is logged, never raised: the caller gets the delete's own result or exception. A missed tombstone is a logged capture gap; a broken `forget` is a user-visible bug. (2026-10-08, #30, founder decision)
- **A filter delete's before/after diff can misattribute concurrent deletes.** A record deleted by another caller during the call is tombstoned as this call's `forget`, and a record added and deleted during the call is missed. Accepted: the storage API returns only a count, and filter deletes are rare, explicit wipes. (2026-10-08, #30)
